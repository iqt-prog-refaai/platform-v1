طرق اتصال تطبيقات الويب (Web Application Communication)

في الدرس 3-1 السابق، تعلمت أن الواجهة الأمامية (Front-end) والواجهة الخلفية (Back-end) تتعاونان معاً لتنفيذ طلب المستخدم. وفي هذا الدرس سنتعرف عملياً على الكيفية التي تنتقل بها الطلبات والاستجابات عبر الشبكة بين العميل والخادم، وما القواعد والرسائل المنظمة لهذا التواصل.

السؤال الرئيسي للدرس
كيف يتواصل العميل والخادم لتشغيل تطبيق الويب، وما القواعد والرسائل التي يستخدمانها؟
الفكرة الأساسية للدرس
تعمل تطبيقات الويب من خلال إرسال العميل للطلبات وإرجاع الخادم للاستجابات، باستخدام بروتوكولات الاتصال (HTTP / HTTPS)، وغالباً واجهات برمجة تطبيقات (API) تتبادل البيانات المهيكلة بصيغ نصية قياسية مثل JSON.

أهداف التعلم الأربعة:

  • 01. شرح نموذج العميل والخادم (Client-Server) وتتبع دورة الطلب والاستجابة خطوة بخطوة.
  • 02. التمييز بين بروتوكولَي HTTP و HTTPS، واستخدام أسلوبَي الطلب GET و POST في سياقات مناسبة.
  • 03. تفسير رموز حالة HTTP الشائعة (200, 404, 500)، وشرح دور API وصيغة JSON في تبادل البيانات.
  • 04. تصميم طريقة اتصال مناسبة لمهمة محددة في تطبيق ويب، وتبرير الاختيار هندسياً.

نموذج العميل والخادم (Client-Server) ودورة الطلب والاستجابة

عندما تنقر على رابط في صفحة ويب أو تبدأ عملية بحث في محرك البحث، يطلب المتصفح البيانات التي يحتاجها من خدمة موجودة على خادم عبر الشبكة. يُسمى هذا النمط نموذج الطلب والاستجابة (Request-Response Model)، ويُعد أساسياً في كثير من تطبيقات الويب.

العميل (Client) الجانب الذي يطلب البيانات أو المعالجة؛ وهو برنامج أو جهاز يرسل طلباً إلى خدمة أخرى. إنشاء وإرسال الطلب (Request) إلى الخادم، ثم استقبال الاستجابة وعرضها للمستخدم. متصفح الويب (Chrome, Safari, Edge) على الحاسوب، أو تطبيق الهاتف الذكي (مثل تطبيق يوتيوب أو تطبيق المدرسة).

بروتوكولا الاتصال HTTP و HTTPS وأمان طبقة النقل TLS

يحتاج التواصل بين العميل والخادم إلى قواعد محددة لتبادل الرسائل عبر الشبكة تُعرف باسم بروتوكولات الاتصال. استكشف في المختبر التالي الفرق الجوهري بين HTTP العادي و HTTPS المحمي بطبقة TLS عبر السيناريو الواقعي لمنصة المدرسة.

المفهوم الأساسي بروتوكول نقل النص التشعبي (HyperText Transfer Protocol) لتبادل الرسائل على الويب. استخدام بروتوكول HTTP عبر اتصال TLS (أمان طبقة النقل - Transport Layer Security) آمن.
حماية المحتوى أثناء النقل ينقل البيانات دون تشفير؛ مما يمكّن المتجسس من قراءة المحتوى أو تعديله بسهولة أثناء النقل. يحمي سرية الاتصال وسلامته ويصادق الخادم، بحيث لا يستطيع المتجسس قراءة المحتوى أو تعديله بسهولة.

الركيزة الأمنية في TLS الخطر الذي تتصدى له الفرق الجوهري في الوظيفة
1. سرية الاتصال (Confidentiality) التنصت وكشف البيانات الحساسة. تمنع المتجسس من قراءة أو فهم المحتوى أثناء النقل (عبر التشفير).
2. سلامة الاتصال (Integrity) التلاعب بالبيانات أو تحريفها في الطريق. تمنع المتجسس من تعديل أو تبديل المحتوى أثناء النقل دون اكتشافه.
3. مصادقة الخادم (Authentication) المواقع الوهمية وانتحال هوية الخادم. تتأكد من هوية الخادم الحقيقي قبل تبادل البيانات معه عبر شهادة TLS الرقمية.

طلبات HTTP والاستجابات: طرق الطلب (GET / POST) ورموز الحالة

يسير التواصل في بروتوكول HTTP وفق قاعدة أساسية: «طلب HTTP واحد، واستجابة مطابقة واحدة». تتضمن الطلبات طريقة طلب توضح نوع العملية (GET أو POST)، وتتضمن الاستجابات رقماً يشير إلى نتيجة المعالجة يُسمى رمز حالة HTTP.

مختبر محاكاة طلبات HTTP ورموز الحالة ● HTTP 200 OK
1. HTTP REQUEST (من العميل)
GET /student/grades.pdf HTTP/1.1
Host: school.edu.eg
[لا يوجد جسم بيانات - طلب استرجاع فقط]
2. HTTP RESPONSE (من الخادم)
HTTP/1.1 200 OK
Side: Client & Server Success
Content: [ملف سجل الدرجات PDF جاهز للعرض]
تحليل العملية: تم استخدام أسلوب GET لأن الغرض هو طلب واسترجاع مورد (سجل درجات الطالب بصيغة PDF) دون إرسال بيانات لمعالجتها، وأعاد الخادم رمز الحالة 200 (نجاح).

اختر سيناريو لتجربته على الخادم:

اضغط على أي موقف لترى طريقة الطلب (GET / POST) ورمز الحالة الناتج (200 / 404 / 500):

الأسلوب الدور والوظيفة الأساسية أمثلة الكتاب المدرسي وأمثلة تطبيقية
GET يُستخدم عادةً لطلب مورد أو بيانات من الخادم (استرجاع وعرض البيانات دون إرسال بيانات لمعالجتها). عرض صفحة ويب، استرجاع نتائج البحث، تحميل سجل درجات الطالب بصيغة PDF، طلب الجدول الدراسي أو توقعات الطقس، تصفح المنتجات.
POST يُستخدم عادةً لإرسال بيانات ليعالجها الخادم (مثل التحقق من بيانات الدخول أو حفظ محتويات النماذج). إرسال معلومات تسجيل الدخول (المعرّف وكلمة المرور)، إرسال محتويات نموذج التواصل، نشر تعليق جديد، أو إنشاء حساب جديد.
رمز حالة HTTP المعنى والدلالة الجانب المرتبط بالنتيجة ومثال واقعي
200 نجاح: تمت معالجة الطلب بنجاح، وأعاد الخادم البيانات أو الصفحة المطلوبة. عملية ناجحة بين العميل والخادم: فتح الصفحة المطلوبة وظهور محتوياتها أمام المستخدم بشكل طبيعي.
404 المورد المطلوب غير موجود بهذا العنوان: الخادم لم يجد الصفحة أو الملف المطلوب في العنوان المحدد. مشكلة من جانب العميل (Client): كتابة عنوان رابط به خطأ إملائي أو النقر على رابط لصفحة أُزيلت من الموقع.
500 خطأ داخلي في الخادم منعه من إكمال الطلب: ولا يحدد الرمز وحده السبب التفصيلي للعطل. مشكلة داخلية في جانب الخادم (Server): تعطل قاعدة بيانات الموقع أو حدوث عطل برمجي داخلي في الخادم.

واجهة برمجة التطبيقات (API) وصيغة البيانات JSON

واجهة برمجة التطبيقات (API - Application Programming Interface) هي واجهة أو عقد محدد للتواصل بين البرمجيات؛ وتُعرّف بأنها مجموعة قواعد واضحة تسمح لبرنامج بطلب بيانات أو وظائف من برنامج آخر، وغالباً تعيد البيانات بصيغة JSON.

مستكشف بيانات JSON التفاعلي (نشاط ص 60) انقر على أي مفتاح (Key) أو قيمة (Value) لتحليله
{
  "city": "Cairo",
  "temperature": 31
}
نشاط «اقرأ البيانات JSON» (صفحة 60): في الكائن {"city": "Cairo", "temperature": 31}:
• المفتاح الأول (Key) هو "city" والقيمة المقابلة له (Value) هي "Cairo" (نص String).
• المفتاح الثاني (Key) هو "temperature" والقيمة المقابلة له (Value) هي 31 (رقم Number).

سؤال «توقف وفكّر» الأول · صفحة 58

لماذا يجب أن تستخدم صفحة تسجيل الدخول HTTPS بدلاً من HTTP العادي؟

فكّر في الركائز الأمنية الثلاث لاتصال TLS قبل إظهار الإجابة النموذجية.

الإجابة النموذجية: لأن صفحة تسجيل الدخول ترسل بيانات حساسة (معرّف المستخدم وكلمة المرور) إلى الخادم؛ واستخدام HTTPS يعتمد على اتصال TLS آمن يحمي:
1. سرية الاتصال: فلا يستطيع المتجسس قراءة كلمة المرور.
2. سلامة الاتصال: يحمي المحتوى من التعديل أثناء النقل.
3. مصادقة الخادم: للتأكد من أن المستخدم يرسل بياناته للموقع الحقيقي وليس لموقع منتحل.
سؤال «توقف وفكّر» الثاني · صفحة 59

إذا استقبل المتصفح رمز حالة HTTP 404، ماذا يجب أن يخبر المستخدم — وأي جانب كانت به المشكلة؟

تذكّر الفرق بين الرمز 404 والرمز 500 من حيث المسؤولية.

الإجابة النموذجية: يجب أن يخبر المتصفحُ المستخدمَ بأن الصفحة أو المورد المطلوب غير موجود بهذا العنوان. وتكون المشكلة مرتبطة بطلب العميل (جانب العميل) (مثل كتابة عنوان URL خاطئ أو طلب رابط لصفحة لم تعد موجودة)، وليست عطلاً داخلياً في تشغيل الخادم.

اشرح خطوة بخطوة ما يحدث عندما يطلب المتصفح صفحة ويب ويستجيب الخادم (6 درجات):

1. العميل (Client): يعمل متصفح الويب بوصفه العميل عندما ينقر المستخدم على رابط أو يطلب عرض صفحة.
2. الطلب (Request): يُنشئ العميل طلباً ويرسله عبر الشبكة إلى الخادم وفق قواعد بروتوكول HTTP أو HTTPS.
3. طريقة طلب HTTP: يتضمن الطلب أسلوب GET لأن الغرض هو طلب واسترجاع مورد (صفحة ويب).
4. معالجة الخادم (Server): يستقبل الخادم الطلب من العميل، ويعالجه بالبحث عن الصفحة المطلوبة وتجهيز بياناتها.
5. الاستجابة (Response): يرسل الخادم استجابة عائدة إلى العميل تحتوي على البيانات المطلوبة (ملفات الصفحة).
6. رمز حالة HTTP: تتضمن الاستجابة رمز حالة مثل 200 للإشارة إلى نجاح معالجة الطلب (أو 404 إذا كان المورد غير موجود).
